# แผน UX และ catalog: SharkTool Demo Suite

เอกสารนี้สำรวจแผง SharkTool Loader ปัจจุบันและเสนอทิศทางสำหรับชุดเครื่องมือใหม่ โดยเน้นการสาธิตในงานประกวด: ผู้ชมต้องเข้าใจประโยชน์ได้ทันที เห็นผลลัพธ์ชัด และผู้สาธิตทำงานสำเร็จได้โดยไม่พึ่งบริการภายนอก

> **สถานะ:** Page Clarity และหน้าเดโมทำ MVP แล้วใน `page-clarity.js` และ `demo.html`; CSS Explainer, Contrast Coach และ Form Map ยังเป็นข้อเสนอ ยังไม่ได้สร้าง

## 1. เป้าหมายการสาธิต

- เปลี่ยนงานที่ต้องเปิด DevTools หรืออ่านโค้ดให้เป็นขั้นตอนที่เริ่มได้จากการคลิก
- แสดงผลก่อน/หลังหรือผลตรวจที่อธิบายได้ ภายในประมาณ 30 วินาทีต่อเครื่องมือ
- ใช้งานได้กับหน้าเดโมที่เตรียมไว้ โดยไม่ส่งข้อมูลหน้าเว็บไปบริการภายนอก
- ให้ผู้ชมใหม่รู้ว่าจะเริ่มตรงไหน และผู้สาธิตกู้คืนหน้าเดิมได้ทันที
- เติมช่องว่างจากเครื่องมือเดิม แทนการทำเครื่องมือ Theme, Monitor, HTTP request, Encryption หรือ Dev Panel ซ้ำ

## 2. UI ปัจจุบัน

แผงลอยถูกสร้างโดย `loader.js` และดึงรายการจาก `manifest.json` มีรูปแบบการทำงานดังนี้:

1. เปิดแผงบนหน้าปัจจุบัน ลากย้ายตำแหน่ง ย่อ หรือปิดได้
2. เลือกธีมหน้าเว็บจากปุ่มชุดบน
3. ค้นหาชื่อ ID หรือคำอธิบาย แล้วเลือกสคริปต์ด้วย checkbox
4. กด **Load** เพื่อโหลดสคริปต์ที่เลือกตามลำดับ พร้อมข้อความสถานะ
5. จำรายการที่เลือกและธีมผ่าน `localStorage` ของหน้าเว็บ

รายการปัจจุบันมี Monitor, Theme, Snipers, BurpShark, SharkScan, Encryption, PostShark และ Dev Panel โดย manifest เป็นรายการแบนที่มี `id`, `name`, `url` และ `description`

### สิ่งที่ควรรักษา

- แผงลอยใช้พื้นที่น้อยและย้ายตำแหน่งได้
- ค้นหาและสถานะผลลัพธ์มีอยู่แล้ว
- มี fallback catalog เมื่อโหลด manifest ไม่ได้
- สคริปต์เครื่องมือแยกจาก loader ทำให้เพิ่มเครื่องมือได้โดยไม่รวม UI ทั้งหมดไว้ในไฟล์เดียว

### ช่องว่างสำหรับผู้ชมงานประกวด

- รายการเป็นชื่อเครื่องมือ ไม่ใช่คำถามหรือผลลัพธ์ที่ผู้ใช้ต้องการ
- ต้องเลือก checkbox แล้วกด Load แม้ต้องการใช้เพียงงานเดียว
- คำอธิบายสั้นยังไม่บอกขั้นตอน เวลา ผลลัพธ์ หรือขอบเขตการทำงาน
- ไม่มีการแยกหมวดหรือแสดงว่าเครื่องมือใดเหมาะกับช่วงสาธิต
- กล่อง log แสดงผลการโหลด แต่ยังไม่ใช่ผลลัพธ์ที่อ่านง่ายสำหรับผู้ใช้ทั่วไป
- แผงมีทั้งเครื่องมือและปุ่มเปลี่ยนธีม จึงควรแยกการปรับหน้าตาออกจากการค้นหางาน

## 3. แนวทาง UX ที่เสนอ

### โครงสร้างและลำดับความสำคัญ

1. **โหมด Demo** เป็นจุดเริ่มต้น: แสดงเครื่องมือแนะนำ 3 รายการเรียงตามลำดับการสาธิต
2. **ค้นหาตามงาน** ใช้คำกริยาที่ผู้ใช้เข้าใจ เช่น “ตรวจหน้า”, “อธิบาย CSS”, “ดูสีให้อ่านง่าย”
3. **หมวดเครื่องมือ** แบ่งเป็น “เข้าใจหน้า”, “ปรับปรุงหน้า” และ “ช่วยงานฟอร์ม”
4. **ปรับแต่ง** ย้ายธีมและการจัดการรายการที่เลือกไว้ไว้ในส่วนรอง ไม่ให้แย่งจุดเริ่มต้น

### รูปแบบการ์ดเครื่องมือ

แต่ละการ์ดควรแสดง:

- ชื่อแบบบอกผลลัพธ์ ไม่ใช้ศัพท์เทคนิคเป็นชื่อหลัก
- ประโยชน์หนึ่งประโยค และเวลาที่คาดว่าจะเห็นผล
- ป้ายกำกับ เช่น “ทำงานในเครื่อง”, “ไม่ส่งข้อมูล” หรือ “เปลี่ยนหน้าเว็บชั่วคราว”
- ปุ่มหลักหนึ่งปุ่ม เช่น **เริ่มตรวจ** หรือ **เลือกองค์ประกอบ**
- ผลลัพธ์ที่คาดว่าจะได้และปุ่ม **ย้อนกลับ** เมื่อมีการเปลี่ยนหน้า

เลือกการ์ดแล้วให้เปิดเครื่องมือนั้นทันที แทนการเลือกหลาย checkbox และกด Load สำหรับกรณีใช้งานทั่วไป ส่วนการโหลดหลายเครื่องมือคงไว้ใน “เครื่องมือทั้งหมด” สำหรับผู้ใช้เดิม

### หลักการโต้ตอบ

- หนึ่งหน้าจอ หนึ่งงานหลัก; ใช้คำไทยตรงไปตรงมาและแสดงศัพท์เทคนิคเป็นรายละเอียดรอง
- เริ่มจากค่าปลอดภัยและหน้าเดโมตัวอย่าง; ไม่คลิก ส่งฟอร์ม หรือแก้หน้าโดยไม่ยืนยัน
- ทุกการเปลี่ยนแปลงมีตัวอย่างก่อน/หลังและทางย้อนกลับที่มองเห็นได้
- สถานะใช้ภาษาบอกความคืบหน้าและผล เช่น “ตรวจแล้ว 12 รูป — พบ 2 รูปที่ไม่มีคำอธิบาย”
- แจ้งข้อจำกัดที่มีผลต่อผลลัพธ์แทนการแสดงสถานะสำเร็จแบบกำกวม
- ใช้งานได้ด้วยคีย์บอร์ด มี focus ที่เห็นชัด และไม่พึ่งสีเพียงอย่างเดียวในการสื่อความหมาย

## 4. Catalog เครื่องมือใหม่ที่เสนอ

ชื่อด้านล่างเป็นชื่อสำหรับผู้ใช้ทั่วไป; Page Clarity ติดตั้งใน catalog แล้ว ส่วนเครื่องมืออื่นเป็นข้อเสนอ

| ลำดับ | เครื่องมือ / ID เสนอ | งานยากที่ทำให้ง่าย | การทำงานหลัก | ผลลัพธ์ที่เห็นบนเวที | ขอบเขต MVP |
|---|---|---|---|---|---|
| 1 | **Page Clarity** (`page-clarity`) | ไล่ดูโครงสร้างหน้าและจุดที่ทำให้อ่านยาก | ตรวจลำดับหัวข้อ ลิงก์/ปุ่มที่ไม่มีชื่อ และรูปที่ไม่มี alt; จัดกลุ่มรายการที่ควรตรวจต่อ | สรุปจำนวนจุดพร้อมรายการกดไปยังตำแหน่งและไฮไลต์บนหน้า | MVP อ่าน DOM อย่างเดียว ไม่ส่งข้อมูลออก ไม่แก้เนื้อหาให้อัตโนมัติ |
| 2 | **CSS Explainer** (`css-explainer`) | เข้าใจว่าองค์ประกอบหนึ่งถูกจัดวางอย่างไรโดยไม่ต้องไล่ CSS เอง | ผู้ใช้เลือกองค์ประกอบ แล้วแสดงขนาด กล่องระยะห่าง display และตัวอักษร พร้อมคำอธิบายภาษาง่าย | คลิกการ์ดบนหน้าแล้วเห็นคำอธิบายและ CSS ที่คัดลอกได้ | อ่าน computed styles; ยังไม่แก้ stylesheet และไม่เปิดเผยค่าใน input/password |
| 3 | **Contrast Coach** (`contrast-coach`) | ตรวจว่าสีข้อความอ่านง่ายหรือไม่ | เลือกข้อความ แสดงสีและอัตราส่วน contrast พร้อมตัวอย่างชุดสีที่อ่านง่ายขึ้น | ตัวเลขก่อน/หลังและ preview แบบเปิด/ปิดได้ | ทดลองเปลี่ยนเฉพาะ preview ชั่วคราว; มี Reset และระบุเมื่อคำนวณพื้นหลังไม่ได้แน่ชัด |
| 4 | **Form Map** (`form-map`) | ทำความเข้าใจฟอร์มยาวหรือซับซ้อนก่อนกรอก | สรุป label, ช่องบังคับ และกลุ่มข้อมูลเป็น checklist | แผนที่ฟอร์มและจำนวนช่องที่ต้องตรวจ | อ่านอย่างเดียว; ไม่อ่าน/บันทึกค่าที่กรอก ไม่ autofill และไม่ submit |

เครื่องมือใหม่ควรอยู่ใน manifest เมื่อมีไฟล์จริงและผ่านการทดสอบแล้วเท่านั้น โดยคำอธิบายสั้นใน manifest ควรบอกประโยชน์ ไม่ใช่ชื่อเทคนิคหรือ URL

## 5. ลำดับส่งมอบ

### Demo MVP

Page Clarity เป็นเครื่องมือแรกของ MVP และมีหน้าเดโมคงที่แล้ว ลำดับถัดไปคือ **CSS Explainer** และ **Contrast Coach**: ทั้งสามทำให้ความซับซ้อนที่มองไม่เห็นกลายเป็นผลลัพธ์ที่เห็นและอธิบายได้ต่อเนื่องกัน

ก่อนเปิดตัว MVP ให้ตรวจว่า:

- แต่ละเครื่องมือมีหนึ่งเส้นทางหลักและเสร็จได้ภายใน 30 วินาทีบนหน้าเดโม
- หน้าเดโมมีตัวอย่างปัญหาที่ตั้งใจไว้ และผลตรวจตรงกับจำนวนที่คาด
- ผู้ชมเห็นความแตกต่างก่อน/หลังโดยไม่ต้องเปิด console
- มีทางย้อนกลับ และการปิดแผงไม่ทิ้ง overlay หรือ listener ที่เครื่องมือเพิ่มไว้
- ถ้าหน้าเว็บมีข้อจำกัดด้าน CORS, CSS หรือ CSP จะบอกสาเหตุ/ข้อจำกัดได้ชัด

### หลังการสาธิต

เพิ่ม **Form Map** หลังยืนยันรูปแบบข้อมูลที่อนุญาตให้แสดงและทดสอบกับฟอร์มหลายชนิดแล้ว จากนั้นพิจารณาหมวดหมู่และข้อมูลเวลา/ความปลอดภัยเพิ่มเติมใน manifest โดยรักษาความเข้ากันได้กับ fallback list

## 6. Run of show สำหรับเวที (ประมาณ 3 นาที)

1. **เปิดโจทย์ (20 วินาที):** “หน้าเว็บซับซ้อน แต่เราไม่ควรต้องอ่านโค้ดทุกบรรทัดเพื่อรู้ว่าควรแก้อะไร”
2. **Page Clarity (45 วินาที):** เปิดหน้าเดโม กดตรวจ แสดงรายการที่พบ และชี้ตำแหน่งบนหน้า
3. **CSS Explainer (45 วินาที):** เลือกองค์ประกอบเดียว แสดงค่าจัดวาง แล้วอธิบายค่าด้วยภาษาทั่วไป
4. **Contrast Coach (45 วินาที):** แสดงตัวเลข contrast ก่อน/หลัง เปิด preview และย้อนกลับ
5. **ปิดการสาธิต (25 วินาที):** ย้ำว่าเครื่องมือทำงานกับหน้าเดโมในเครื่อง ไม่ส่งเนื้อหาออก และผู้ใช้เป็นผู้ตัดสินใจทุกการเปลี่ยนแปลง

เตรียมหน้าเดโมสำรองไว้ในเครื่องและทดสอบการโหลดก่อนขึ้นเวที ไม่พึ่งเครือข่ายหรือหน้าเว็บของบุคคลที่สามเป็นองค์ประกอบสำคัญของการสาธิต

## 7. เกณฑ์ความสำเร็จของ UX

- ผู้เข้าร่วมใหม่เริ่มเครื่องมือแรกได้ภายใน 10 วินาทีโดยไม่ต้องมีคนบอกว่าควรกดอะไร
- ผู้ชมอธิบายประโยชน์ของเครื่องมือแต่ละตัวได้จากชื่อและการ์ด โดยไม่ต้องรู้ศัพท์ DevTools
- ผลลัพธ์แรกปรากฏภายใน 30 วินาทีบนหน้าเดโมที่เตรียมไว้
- ไม่มีการส่งเนื้อหาหน้าเว็บหรือค่าฟอร์มออกเครือข่ายใน MVP
- ทุก preview หรือการเปลี่ยนแปลงชั่วคราวย้อนกลับได้ด้วยการกระทำที่เห็นชัด
- การค้นหาด้วยคำทั่วไปพบเครื่องมือที่ต้องการโดยไม่จำเป็นต้องจำชื่อผลิตภัณฑ์
